## Mandatory Oracle Specification

## Test Structure

Follow **Arrange-Act-Assert** (AAA) pattern:

```typescript
describe('[UnitUnderTest]', () => {
  describe('[methodName]', () => {
    it('should [expected behavior] when [condition]', () => {
      // Arrange
      const input = createTestInput();

      // Act
      const result = unitUnderTest.method(input);

      // Assert
      expect(result).toBe(expectedValue);
    });
  });
});
```

## Test Naming

- **Format:** `should [expected behavior] when [condition]`
- **Good:** `should return user when valid email provided`
- **Bad:** `test user`, `works correctly`, `handles error`

## What to Test

| Layer | What to Test | What NOT to Test |
|-------|-------------|-----------------|
| Domain | Business rules, invariants, state transitions | Getters/setters, constructors (unless complex) |
| Application | Use case orchestration, error mapping | Framework wiring |
| Infrastructure | Repository queries, API contract compliance | Third-party library internals |

## TDD Enforcement

Follow RED-GREEN-REFACTOR for every task:
1. **RED** — Write a failing test that defines the expected behavior
2. **GREEN** — Write the minimum code to make the test pass
3. **REFACTOR** — Clean up while keeping tests green

**Iron Law:** No production code without a failing test first.

## Test Data

- Use factory functions for test data (e.g., `createTestUser()`)
- Never hardcode IDs or timestamps in tests
- Use meaningful test data that represents real scenarios
- Keep test fixtures in `tests/fixtures/`
